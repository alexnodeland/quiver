# WASM Bindings

This directory contains WebAssembly bindings for running Quiver in browser environments.

## Overview

The WASM module provides a JavaScript-facing API via `wasm-bindgen`, enabling:
- Full Quiver functionality in web browsers
- Audio worklet integration for low-latency processing
- TypeScript type generation via `tsify`
- MIDI and real-time parameter control

## Files

```
wasm/
├── mod.rs              # Module entry point, re-exports
├── engine.rs           # QuiverEngine - main WASM interface
└── error.rs            # QuiverError - error handling for JS
```

## QuiverEngine API

The `QuiverEngine` struct is the main interface exposed to JavaScript. All method
names below are the exact JS names (wasm-bindgen snake_cases them from Rust).

### Lifecycle
- `new(sample_rate)` — Create a new engine
- `free()` — Release the engine (auto-generated by wasm-bindgen). Call this when
  done; it is **not** optional in long-lived apps. Guard against double-free.

### Audio processing
- `tick()` → `Float64Array` `[left, right]` — process one sample
- `process_block(num_samples)` → `Float32Array` of length `num_samples * 2`
  (interleaved `[l0, r0, l1, r1, …]`). **Ownership rule:** the returned array is a
  *view into WASM memory*, valid only until the next engine call or `free()`. Copy
  it immediately (`Array.from(...)`, `myBuf.set(...)`) if you need to retain it.
  Output is safety-clamped to ±10V.
- `reset()` — reset all module state
- `compile()` — explicitly compile (usually unnecessary: `tick`/`process_block`
  lazily recompile a dirty graph). Surfaces compile errors eagerly.
- `set_observer_interval(blocks)` — collect observer state every N blocks
  (default 8; min 1). Decimates real-time state collection off the audio path.

### Patch management
- `load_patch(json)` — load a `PatchDef` (replaces the current patch atomically)
- `save_patch(name)` → `PatchDef` — serialize the current patch
- `validate_patch(json)` → `ValidationResult`
- `clear_patch()` — reset to an empty patch

### Module operations
- `add_module(type_id, name)` — add a module
- `remove_module(name)` — remove a module and its cables
- `set_output(name)` / (checked routing happens in the graph layer)
- `set_module_position(name, x, y)` / `get_module_position(name)` → `[x, y]`
- `module_count()` / `cable_count()` / `get_module_names()` → `string[]`
- `get_params(name)` / `get_param(name, index)` → number /
  `set_param(name, index, value)` / `set_param_by_name(name, param_name, value)`
- `get_port_spec(type_id)` — port spec for a module *type*

### Cable operations
- `connect(from, to)` → `number` — connect two `"module.port"` refs; **returns the
  new cable's stable `CableId`** (a number)
- `connect_attenuated(from, to, attenuation)` → `number`
- `connect_modulated(from, to, attenuation, offset)` → `number`
- `disconnect(from, to)` — disconnect by port refs
- `disconnect_cable(cable_id)` — disconnect by the stable id from `connect`
- `disconnect_by_index(index)` — disconnect the cable at a list position (resolved
  to its stable id internally)

### Catalog & signal semantics
- `get_catalog()` / `search_modules(query)` / `get_modules_by_category(category)` /
  `get_categories()`
- `get_signal_colors()` / `check_compatibility(from_kind, to_kind)` — kinds are the
  snake_case strings `audio | cv_bipolar | cv_unipolar | volt_per_octave | gate |
  trigger | clock`

### MIDI integration
The MIDI methods drive engine-owned CV source modules so notes actually affect
audio once cabled:

- `add_midi_inputs()` — inject `midi_voct`, `midi_gate`, `midi_velocity`,
  `midi_mod`, `midi_bend` `ExternalInput` modules (each with an `out` port). Cable
  e.g. `midi_voct.out` → `vco.voct`, `midi_gate.out` → `adsr.gate`. Idempotent.
- `midi_note_on(note, velocity)` / `midi_note_off(note, velocity)` — update pitch
  (V/Oct), velocity (0–1) and gate (5V/0V) CV sources.
- `midi_cc(cc, value)` — CC1 (mod wheel) drives `midi_mod`. `get_midi_cc(cc)` reads
  the stored 0–1 value.
- `midi_pitch_bend(value)` — `value` in -1..1, drives `midi_bend` as a ±2-semitone
  V/Oct offset.
- Read-only getters: `midi_note` (V/Oct), `midi_velocity` (0–1), `midi_gate`
  (boolean), `pitch_bend` (raw -1..1), `sample_rate`.

Note: the injected MIDI input modules are engine-managed and not in the module
registry, so a patch saved while they are present cannot be reconstructed by
`load_patch` on a fresh engine — call `add_midi_inputs()` again after loading.

### Real-time state bridge
- `subscribe(targets)` / `unsubscribe(target_ids)` / `clear_subscriptions()`
- `poll_updates()` → `ObservableValue[]` / `pending_update_count()`

## Building

```bash
make wasm            # Build WASM glue (release) into packages/@quiver/wasm/
make wasm-dev        # Faster dev build
make wasm-check      # Type-check for the wasm target
```

`make wasm` emits `quiver.js`, `quiver.d.ts`, `quiver_bg.wasm`, `quiver_bg.wasm.d.ts`
into `packages/@quiver/wasm/`. The npm package's tsup build (`npm run build
--workspace @quiver/wasm`) then compiles `src/index.ts`, `src/audio.ts` and
`src/worklet.ts` on top of that glue into `dist/`.

## Feature Flag

Gated behind the `wasm` feature (which implies `alloc`). Enables `wasm-bindgen`,
`tsify`, `serde-wasm-bindgen`, `js-sys`, and `console_error_panic_hook`.

## Integration Notes

### Thread safety
Single-threaded (no `Send`/`Sync`). The AudioWorklet runs on its own thread and
communicates with the main thread by message passing (see `@quiver/wasm`'s
`audio.ts` / `worklet.ts`); the engine instance lives entirely inside the worklet.

### Memory management
Managed by WASM linear memory. Call `free()` on engines you own. `process_block`
returns a view into that memory — see its ownership rule above.

### Performance
- `process_block` uses preallocated, reused buffers and `Patch::tick_block` (no
  per-block/per-sample allocation in steady state).
- Observer collection is decimated (`set_observer_interval`).
- Avoid allocations in the audio path; `console_error_panic_hook` improves traces.
